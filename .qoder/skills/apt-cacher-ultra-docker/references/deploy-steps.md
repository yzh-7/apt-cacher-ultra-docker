# 部署细节

## 部署形态只有两种，先选对

| 形态 | 代理端口 | 管理端口 | 用途 |
|---|---|---|---|
| poc | `127.0.0.1:16790` | `127.0.0.1:16789` | 与现有缓存并行试点，绑 loopback，外部访问不到，也不抢端口 |
| prod | `3142` | `6789` | 正式接管客户端流量；必须先停掉现有实例并取得用户同意 |

默认 poc。任何直接上 prod 的动作都属于用户决定，不属于你。

## 三处必须继承，漏了就是另一个服务

1. **CA 在 `<cache.dir>/ca`**。里面是私钥和已签发的证书链。换 cache 目录而没带过去，等于换 CA：所有信任旧 CA 的客户端立刻开始报错。旧 CA 的指纹用容器命令打印出来核对，别凭记忆。
2. **主机密钥环要 bind-mount，而且要写进配置里的 `keyring_dirs`**。只做挂载不写进配置，密钥数量不会变；只写配置不挂载，路径不存在。两项都要有。检查方法是看状态页的密钥数量，以及冒烟测试里"至少一把密钥来自挂载路径"这一项。
3. **`network_mode: host`**。桥接网络会让上游看到 Docker 的出口地址，缓存日志里的 `client_addr` 也不再是真实客户端，按客户端排查问题时就瞎了。

## 目录与权限

- 容器以 `113:112` 运行。缓存目录必须 `0750` 且属主 `113:112`，否则守护进程启动即退出：日志里是 `load config: cache.dir ...: not writable`。
- 目录非空时不要 `chown -R`：那会连带改掉已有缓存内容的所有权。已有内容的目录要么原本就正确，要么就该换目录。
- 根文件系统只读 + `/tmp` 用 tmpfs：容器运行期写什么都落在 tmpfs 里，重启即净空，这是设计。
- 挂载一个主机上不存在的路径时，Docker 会把它创建成目录。密钥环挂载前先确认源路径存在且非空；`/etc/apt/keyrings` 里 0 字节的 keyring 文件是真实存在过的坑。

## 备份

真正不可重建的只有 `<cache.dir>/ca`（私钥 + 证书链）。blobs 丢了就是回源重取，`state.db` 丢了就是重新索引。所以备份策略可以很小：`ca` 目录 + 配置文件，其余按需。

## 客户端接入

用 `assets/apt-proxy.conf`。要点：源保持真实主机名，代理指过去；把源写成缓存地址会得到 `400 Bad Request`。HTTPS 源要等客户端信任缓存 CA 之后再走缓存，否则 `The certificate issuer is unknown`。

## 验证才算完成

`scripts/verify.sh` 十项全过。任何一项失败都别把服务报成交付完成——这台机器上出现过"服务起来了但密钥环 0 把、快照永不采纳"的形态，只看 healthz 是查不出来的。
